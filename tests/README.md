# tests/

Cross-package test suites, run with one command from the repo root: `pnpm test` (`npm test` runs the same script once `pnpm install` has been done; the repository refuses `npm install`).

Unit tests live next to the code they cover (`*.test.ts` inside each package). This folder holds the suites that span packages:

- golden runs over the synthetic documents in `samples/` (expected clause hits, dates, escalation states), `tests/golden/questions.ts` + `ask.test.ts` (questions about the documents: the clause each answer must come from, or that it must be refused), and `tests/golden/pipeline.test.ts`, the whole pipeline over HTTP (below)
- adversarial cases: prompt injection inside documents, XSS payloads, hostile uploads, safety-escalation routing, route guards, a second reader on the same browser, a double-pressed sign-in, the ask screen (`ask-screen.test.tsx`: a safety cue in a question, a statement citing a passage the API did not send, a model outage, a lost session)
- schema-rejection cases: malformed or uncited model output must be refused, never rendered
- accessibility checks: `tests/a11y/` pins the route-level behaviour (focus on route change), the display controls (the language toggle leaves every statement and excerpt byte-identical, text size scales and persists, read-aloud speaks and stops through a stubbed `speechSynthesis`) and what the whole-screen read-aloud says (never a withheld statement) in a DOM; the keyboard-only journey and the axe scan run against a real browser with `pnpm a11y` (below)

All suites run offline against the mock LLM adapter; no test may call a hosted model.

## One command, six layers (`pnpm test`, PRD §12)

`vitest run` at the root runs every `*.test.ts` / `*.test.tsx` under `artifacts/`, `lib/` and `tests/` as one vitest project per PRD §12 layer, so each file is printed with its layer (`|golden|`, `|unit|`, ...) and the run ends with a per-layer table after vitest's own summary:

```
 Test layers (PRD §12)
  ✓ Golden documents    8 files    78 tests  passed
  ✓ Adversarial        10 files   119 tests  passed
  ✓ Accessibility       6 files    34 tests  passed
  ✓ Schema              6 files    63 tests  passed
  ✓ Integration        14 files   179 tests  passed
  ✓ Unit               39 files   563 tests  passed
  all layers passed · 83 files · 1036 tests · 47.8s
```

(The run of 18 September 2026.) `pnpm test:coverage` is the same run under V8 coverage of the product code, with a text summary at the end and an HTML report in `coverage/` (git-ignored); the include and exclude lists are in the root `vitest.config.ts`. `pnpm preflight` runs the build, this suite, the client secret scan and the repo-size ceiling in one go, and `.github/workflows/ci.yml` runs the same four steps on GitHub.

Which layer a file belongs to is decided in one place, `scripts/test/layers.ts`: an ordered table of directories and single files, first match wins, `unit` is the catch-all. The vitest include/exclude globs and the reporter (`scripts/test/layer-summary.ts`) are derived from that table, and `tests/support/layers.test.ts` walks the disk to check that every test file resolves to a layer and every layer has files, because a file that matched no project would otherwise never run and nothing would say so. Layers that need more than a path: `lib/rules/src/untrusted.test.ts` (instruction-like document text) is adversarial although it sits beside the rules' unit tests, and the model adapters under `api-server/src/llm/` are schema tests because what they check is that model output is validated, retried and refused before anything is rendered. A failing layer shows `×` and vitest exits 1; `pnpm test -- <path>` filters as usual and the layers it skips show as "no files in this run".

## Golden documents through the pipeline (`tests/golden/pipeline.test.ts`)

The function-level goldens (`clause-rules`, `retrieval`, `document-map`, `review-prompts`, `compare`, `claims`) pin what each stage selects without the HTTP layer. `pipeline.test.ts` runs the same fixtures the way the browser sends them: each of the three documents is uploaded to the real API as the committed text, and as a PDF (40 lines a page) and a DOCX generated from that text at test time, then `document-map` and `review-prompts` are requested; the comparison pair (`rental-agreement-synthetic.txt` against `rental-agreement-v2-synthetic.txt`) goes through `compare` as text and as two PDFs.

What the tables pin, hand-written from the fixtures, is what the product decides on its own: every cited paragraph (the clause label the reader sees, its 1-based paragraph, its opening words so a row can be checked against the file, and for the PDF the first paragraph of every page), each field's evidence, every timeline date with the wording it was read from, every prompt's rule, the paragraph its question rests on and the places it lists, the not-found list, and all seven differences between the drafts with their kind, signals, paragraph on each side, extracted values and the words that differ. The mock model's wording is checked for shape only: a statement must quote its cited paragraph verbatim and carry the mock's marker, timeline entries and places are the paragraph's own words, and a field's statements cite its evidence in order. The PDF and DOCX runs must equal the text run once page numbers are removed.

Writing this suite found a real extraction bug: a PDF page holding only one-line paragraphs (the NDA's signature block alone on the last page) came back as one chunk, because a page like that has no wrapped line to reveal its line pitch and the paragraph spacing was taken for it. The PDF reader now measures the document's usual pitch (the most frequent line gap across all pages, `extraction/pdf.ts` `documentPitch`) and uses it for such a page; the golden pins 53 paragraphs for the NDA in every format.

## Adversarial suites (`tests/adversarial/`, PRD §9)

All run against the real API with the mock provider; the two fixture documents are in `samples/adversarial/` and are not in `manifest.json` on purpose (the upload suite builds its hostile files in memory).

- `prompt-injection.test.ts` — the injection fixture (instructions to an AI spliced into the deposit, notice and termination clauses: the PRD's own sentence, a role-play, a JSON break-out, a forged chunk id, a demanded verdict, a fake validator line, one in Hindi) goes through `document-map` and `review-prompts` at every stage with the provider wrapped to keep each request. It proves the policy and the pipeline's own lines are unchanged, the injected clauses reach the model only as strings inside the excerpt array, a claim that obeys them is withheld by the validator (forged id → `unknown-chunk`, recited policy → `instructions-echoed`, whole, in four-word pieces across claims, or with a word altered every so often), and no response carries prompt text (`tests/support/prompt-artifacts.ts`). The last block switches the wrapped provider into a model that obeys the clauses and runs the same routes: the responses still come back 200 with the honest restatements only, `withheld` counts the rest, and the retry feedback names nothing of the prompt or the document.
- `upload-hardening.test.ts` — the four PRD §9 upload cases against both routes that take files (`/documents/extract`, `/sessions` in single and compare slots), sent the way a crafted client would send them (fetch's own multipart encoding, and a hand-built body for names fetch would escape): a file whose bytes are not what its extension says (PDF/DOCX/PNG/text in every wrong combination, with truthful and lying MIME headers) → 415 `format-mismatch`; a 10 MiB + 1 file → 413 `too-large` while it streams, before its type is looked at; a zero-byte file under any extension → 422 `empty`; a name that is a path (`../../etc/passwd`, backslashes, drive letters, `..`, `..` behind a right-to-left override, a header-decoded newline, a tab, a NUL, 300 characters, blank) → 400 `bad-filename` (or the parser's own 400 for the NUL), with the naive landing spots in the working and temp directories checked before and after, `/etc/passwd` unchanged, no session opened and no refusal message repeating the name. Odd but honest names (Devanagari, a right-to-left override, surplus whitespace, 200 characters) are accepted and shown cleaned. The suite ends by checking both gates are empty, an honest upload still works, and no `uncaughtException`/`unhandledRejection` fired in the process hosting the API. Nothing an upload sends is written to disk anywhere in the API, which is the reason no traversal is possible; the suite checks the file system anyway.
- `xss-rendering.test.tsx` — the XSS fixture (script tags, event handlers, `javascript:` links, an iframe, a page-blanking stylesheet, encoded variants) with a hostile file name is uploaded, then the real screens are mounted under happy-dom against the API: map with every source opened, review prompts with places and paragraphs opened, packet (download checked as a `text/plain` blob), version comparison, upload. Every payload must be visible as text and nothing may be live: no foreign element, no `on*` attribute, no script URL, no outside address, `window.__xss` unset. The DOM does not run scripts, so a browser walk confirms execution: start the API from a shell with the mock provider (replit.md Gotchas), upload `samples/adversarial/xss-clause-synthetic.txt`, take the calm sample answer, and walk map → review → packet → compare with the console open — no dialog, no error, `window.__xss` undefined, page not blanked. Last done with Chromium on 15 Sep 2026: zero findings on every screen.

The happy-dom suite boots the API as a tsx child process (`tests/support/api-server.ts`, `bootApiProcess`) because vitest rewrites `import.meta.url` under a DOM environment and the extraction worker cannot be found in-process.

## Accessibility audit (`pnpm a11y`, Task 7.1)

`scripts/a11y/journey.mjs` drives the whole journey with the keyboard alone in a headless Chromium (`playwright-core` on the system browser, `CHROMIUM_PATH`, default `/repl/tools/bin/chromium`; the page's mouse is disabled at the driver level, so any pointer use is a bug in the audit). Three journeys — single document (welcome → upload, including the missing-file, refused-file and missing-consent states → interview → map with a source opened → review prompts expanded → packet with a reference followed, the bypass link, print and the text download → delete), version comparison (two files, one removed and re-added → compare → packet → delete), and helplines / safety escalation / not-found. On every screen state reached it records the full Tab order with each stop's accessible name, on-screen position and focus indicator (focused styles compared with the same element unfocused), and runs axe-core (WCAG 2.0/2.1/2.2 A+AA and best-practice) in light and dark mode. The packet's neutral palette is `oklch()`, which axe cannot parse; those nodes get the same 4.5:1 / 3:1 check by the script, with the browser doing the colour parsing.

It exits 1 on any critical or serious axe violation, a reached control without a name or a visible focus indicator, focus left off screen, or a step that cannot be completed from the keyboard; moderate and minor axe findings are printed as advisory. The report (`report.json`, `tab-order.md`) lands in `scripts/a11y/report/` (ignored by git). It needs the web client and the API running with both offline stand-ins, the model's and sign-in's (real Google or e-mail sign-in cannot be driven headlessly): from `artifacts/api-server`, `PORT=8091 LLM_PROVIDER=mock AUTH_PROVIDER=mock npx tsx src/index.ts`, and from `artifacts/clausecompass`, `PORT=5191 BASE_PATH=/ API_PROXY_TARGET=http://127.0.0.1:8091 VITE_AUTH_PROVIDER=mock pnpm run dev`; then `BASE_URL=http://127.0.0.1:5191 pnpm a11y` (`BASE_URL` defaults to `http://localhost:80`, the workspace proxy, which serves the real sign-in). The runner's sign-in step expects the stand-in's "Continue with Google" to sign a reader in at once. `A11Y_JOURNEYS=single-document` runs one journey. It is not part of `pnpm test`, which stays offline and browser-free. Last full run on 17 Sep 2026: 27 screen states, 0 findings.
