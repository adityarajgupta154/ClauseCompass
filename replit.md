# ClauseCompass

GenAI legal document navigator for India (Hack2Skill 2026, "AI for Legal Assistance & Access"): explains an uploaded offer letter / rent agreement / NDA in plain language (the three document types in `lib/rules` `DOCUMENT_TYPES`; no ToS), flags the clauses and dates that matter for the user's situation, says nothing that is not tied to a cited excerpt (there is no free-text Q&A), compares two versions, and produces a source-cited preparation packet for a lawyer or official legal-aid service. Information, never legal advice.

## Run & Operate

- On Replit: the two workflows `artifacts/api-server: API Server` (port 8080, serves `/api`) and `artifacts/clausecompass: web` (port 20162, serves `/`) run the app; the platform injects `PORT`/`BASE_PATH`.
- Locally (judges/contributors, macOS/Linux/WSL): `pnpm dev` at the repo root starts both (API `:8080`, web `:5173` with a Vite proxy for `/api`). `API_PORT` / `WEB_PORT` override the ports.
- `pnpm test` (or `npm test`) — every test in the workspace in one command (vitest, root `vitest.config.ts`: `*.test.ts`/`*.test.tsx` under `artifacts/`, `lib/`, `tests/`), offline, ~50 s. The files run as one vitest project per PRD §12 layer — golden, adversarial, accessibility, schema, integration, unit — decided by the path table in `scripts/test/layers.ts` (first match wins, `unit` is the catch-all), each file is printed with its layer, and `scripts/test/layer-summary.ts` ends the run with a per-layer files/tests/pass-fail table; `tests/support/layers.test.ts` fails if a test file on disk maps to no layer or a layer has no files. `pnpm test -- <path>` filters as usual (empty layers then show as "no files in this run"). `pnpm run typecheck` — full typecheck. `pnpm run build` — typecheck + build all packages; the web build needs `PORT` and `BASE_PATH` set (Replit's deploy supplies them; locally run `PORT=5173 BASE_PATH=/ pnpm run build`).
- `pnpm test:coverage` — the same suite under V8 coverage of the product code (include/exclude in `vitest.config.ts`; tests, `src/testing/`, `pages/dev/` excluded), text summary + HTML in `coverage/` (git-ignored). No threshold; 17 Sep 2026: 86.9% statements, 79.2% branches.
- `pnpm lint` — ESLint flat config at the root (`eslint.config.mjs`, ESLint 10; `eslint-plugin-jsx-a11y` 6.10 still declares a peer range ending at 9, allowed in root `package.json` `pnpm.peerDependencyRules` — it runs fine on 10, and ESLint 9 is deprecated on npm): `@eslint/js` recommended + `typescript-eslint` recommended everywhere; `react-hooks` recommended (v7: also `refs`, `immutability`, `set-state-in-effect`) and `jsx-a11y` strict for the web app and the `.tsx` tests; `no-console` (warn/error allowed) in the web app's product code. Generated code and `dist/` are ignored. The three `eslint-disable-next-line` comments in the web app each carry the reason; do not add one without a reason. Runs in ~20 s.
- `pnpm preflight` — `scripts/preflight.sh`: build → lint → test → check:client-secrets → check:size (size last so it cannot hide a secret finding), stops at the first failure, defaults `PORT`/`BASE_PATH` for the web build. `.github/workflows/ci.yml` runs the same four on push/PR to `main` (Node 22 + 24) plus `pnpm audit --audit-level=high` as a separate job.
- `pnpm check:size` — fails if the shippable repo payload (tracked + untracked-not-ignored) exceeds 3 MiB. Failing since 17 Sep 2026 (about 3.5 MB after the 17 Sep cleanup, the user chose to leave it red for now); raising the ceiling or trimming the tree is the user's call, not yet taken.
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm check:client-secrets` — greps the web client source, builds the bundle, greps that too; fails on any server-secret name (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `SESSION_SECRET`, `sk-ant-`).

## Environment

It is deterministic and calls no model (`src/analysis/compare/`): `align.ts` pairs paragraphs by a monotonic weighted-LCS over word-bigram Dice similarity (≥ 0.6, or ≥ 0.2 when both carry the same clause label; ties prefer "added" so a replaced block reads removed-then-added; a second pass pairs a gap holding exactly one removed and one added paragraph when they share ≥ 0.3 of their single words, for short unnumbered lines; a moved clause therefore shows as removed + added — a known limit; more than `MAX_ALIGN_CELLS` = 4M paragraph pairs, about 2,000 a side, is refused with 422 `too-complex` before any table is allocated, and the adversarial all-similar case at the cap runs in ~0.2 s), `diff.ts` is a word-level LCS whose per-side segments concatenate back to the paragraph exactly (token keys ignore punctuation at a word's edges so a moved comma is not a change, but when that pass sees nothing and the normalised texts still differ it re-runs with exact keys, so a punctuation-only edit is reported as wording), `classify.ts` counts weighted detectors (amounts, durations, dates, remedy vocabulary, duty modals, party swaps) only where they overlap a changed span, picks the heaviest kind with a fixed tie precedence money > time > remedy > duty > wording, and returns the leading kind's verbatim matches as `values` so the client never re-detects. The server returns kinds and values; every sentence the reader sees comes from `copy.compare`. `tests/golden/compare.test.ts` pins the rental v1 → v2 change list (seven changes, incl. the late-fee and notice-period cards the acceptance line asks for), self-compare = no changes, reverse symmetry, and lints the compare copy.

  - Decision flow (PRD §8 table), `src/flow.ts`: states `awaiting-stage → review → urgent-review`, plus `safety-escalation`, which is absorbing (every later event returns the same state; a new session is a new machine). Events: `stage-chosen`, `user-said { text, origin: interview|question }`, `deadline-known { date: YYYY-MM-DD, origin: user|document, label? }`; the caller passes `{ today }`. `transition`/`applyEvents` step the machine; `decide(context, clock)` decides from a snapshot independent of the order facts arrived (every user text is scanned and the cues combined in lexicon order before escalation; same-day deadline ties are broken by content: user over document, labelled over unlabelled, then label text), and returns a `Decision`: `documentAnalysis run|skip|wait`, the stage's `plan` (`src/stage-plans.ts`: family priority order, interview `asks` keys, `outputs` views), `lookFor` (registry rules for the stage, primary block first, each block in the plan's family order), `urgency` (closest deadline with `daysLeft ≤ 7`, past-due counts, upcoming beats past-due; `answerStyle: brief`, `adviseOfficialContact`), `safety` (category, cues, guidance *keys* — the numbers live in the FR-10 resource registry). ## Architecture decisions

- Pipeline is document → deterministic rule/state-machine decision → LLM plain-language rewrite in strict JSON → citation-gated rendering → human/official handoff. Rules decide *what* to surface; the model only rephrases selected evidence.
- Grounding is mechanically verifiable: every claim must cite chunk ids and carry a verbatim quote that the validator finds inside the cited chunk; anything failing is refused, not rendered.
- Sign-in gates the document journey only (`/upload` and every screen after it); Welcome, `/help`, `/safety` and Not found stay open, so a helpline is never behind a login. Firebase Authentication (Google + e-mail/password) issues the identity; the API verifies the ID token itself with `jose` (no firebase-admin, no service account, nothing of Firebase's runs on the server) and binds each session to the signed-in uid. Sessions are still memory-only with a short TTL and the user re-uploads; the account marks a session as theirs, it does not make it persist. Storage sits behind a single `SessionStore` interface (in-memory first, swappable).
- Retrieval is lexical (hand-rolled BM25 over chunks), no vector DB. Documents are small; determinism and zero infra win.
- LLM access goes through a provider adapter with a `mock` implementation so the whole test suite runs offline; a cheap hosted schema-constrained model is used at runtime (default `claude-haiku-4-5`; the Anthropic Messages API is called over `fetch` with a forced tool call rather than an SDK, so the same adapter serves a hand-set key and the Replit Anthropic AI integration). The model output is checked by `validateModelOutput` before anything else touches it; the one retry carries the validator's findings; provider errors are not retried (per-client rate limiting and the PRD's single stronger-model escalation on low confidence are later tasks — `ClaimRequest.model` is the hook).
- PDF export uses a print stylesheet, no PDF library. Uploads are magic-byte checked, size- and page-capped, text-only extraction; nothing an upload sends is ever written to disk (memory storage only, no `fs` writes anywhere in the API).
- Extraction unit = paragraph. A chunk is `{ text, page, paragraphIndex }`: whitespace collapsed, `paragraphIndex` 1-based across the whole document (this is `SourceLocation.paragraph`), `page` 1-based for PDF and `null` for DOCX/TXT (Word has no fixed pagination). TXT/DOCX paragraphs split on blank lines / Word paragraphs; PDF paragraphs are recovered from layout: runs are placed in their own reading frame and grouped by orientation (body text first, rotated watermarks/margin notes after it), runs on a line are put in visual order (right-to-left for RTL), a paragraph starts at a line gap > 1.3× the line pitch, at an upward jump, or at a clause number after a short line; the pitch is the page's smallest plausible gap measured in font sizes, except that a page whose gaps are all the same and clearly wider (> 1.3×) than the document's usual pitch (the most frequent plausible gap in the whole document, `documentPitch`, so one tight letterhead or a double-spaced body cannot skew it) takes the document's — a signature block or a run of one-line clauses alone on a page has no wrapped line of its own to reveal its pitch and would otherwise collapse into one chunk; a paragraph that continues over a page break becomes two chunks so every chunk's page stays exact. Multi-column PDFs are a known limitation. Limits: 10 MB, 50 pages, 30,000 words (PDF reading stops early past 250k characters), a .docx is inflated under a 50 MB / 5,000-entry budget before mammoth opens it (declared sizes are not trusted, so forged zip bombs stop at the budget), and a PDF with < 40 characters of text is refused as a scan (`no-text`). Refusals are `ExtractionError`s with a code (`unsupported-format`, `format-mismatch`, `encrypted`, `malformed`, `no-text`, `too-large`, `too-long`, `too-complex`), an HTTP status and a user-facing message; parser exceptions stay in `cause` and only their class and category reach the debug log.
- Parsing runs in a worker thread per document (`extraction/isolated.ts` → `extraction/worker.ts`, bundled as `dist/extraction/worker.mjs`; tests load the `.ts` worker through tsx) with a 256 MB heap cap, a 30 s deadline and a process-memory watch (`extraction/memory-watch.ts`: while workers run, resident size is polled against 75% of the cgroup/physical limit and running workers are stopped past it, because V8 heap caps do not cover the typed arrays decoders fill). Any of these ends only that worker and answers `too-complex` (422). Routes call `extractDocumentIsolated`, never `extractDocument`, for uploaded bytes. Two in-process gates (`middlewares/extraction-gate.ts`): at most 32 uploads buffering at once (taken before the body is read, so a flood cannot fill memory with 10 MB bodies) and 2 documents parsing with 16 waiting (taken after the file has arrived, so a slow connection cannot occupy a parser); past either → 503 `busy` with `Retry-After`. `Gate.acquire(places)` takes several places in one step (the compare route takes 2 upload places; a half-held pair could deadlock two compares against each other) with FIFO waiters, and the compare route parses its two files one after the other through the parse gate. The HTTP server's `headersTimeout`/`requestTimeout` (30 s / 120 s) bound how long an upload may hold its place. Not covered yet: per-client rate limiting (a later task).
- Minimal dependencies on purpose (repo must stay small and auditable); Zod is the one schema tool for everything.

Preparation Packet (`/packet`, FR-09, PRD §5 step 7; reached from the review page's "Continue" link, or from the compare page's for the compare stage, where it covers the newer version; guarded like the other analysis routes): `features/packet/build-packet.ts` folds the map response and the review-prompts response into one pre-phrased `Packet` model with no model call — summary (the six map fields, one `resolveClaim`-checked statement per finding, withheld statements shown as such), dates (grouped by day, ambiguity noted), questions (the review prompts by relevance, claim + "Found at" places), an evidence checklist (deterministic: fixed lines, per-stage lines, then one line per clause family present in the prompts, citing that family's places — the PRD names the checklist but does not define it) and citations (numbered in order of first use across the whole packet, listed once with the verbatim excerpt + `formatLocation`). `packet-document.tsx` renders it as a fixed light paper sheet in both themes (`PacketDocument`, pure React), `render-text.ts` as the plain-text download (`renderPacketText`; headings are never uppercased so every model string appears verbatim), `packet-strings.ts` lists every reader-facing string for tests, `use-packet.ts` combines the two queries into one `AnalysisState`. `pages/packet.tsx` adds the actions (`window.print()` — "save as PDF" is the browser's dialog — and a Blob download named `clausecompass-packet-<file>.txt`). Print: `AnalysisScreen`'s `printsBodyOnly` hides the app chrome, `index.css` sets `@page` A4 / 15 mm and a white body under `@media print`, the citations section starts on a new page. The boundary statement sits on the sheet itself (top notice + closing section), not only in the app. Features land task by task from the user's build breakdown.
- Responsible language (PRD §8 / FR-06): the product asks the reader to review or confirm a term; it never says a clause is illegal, invalid, unenforceable, that the reader will win, is entitled, or should sue. The table lives in `lib/grounding/src/language.ts` and is enforced in code at every point a sentence is constructed — registry data (invariant check), model output (validator rejection + one retry with the reason), the review-prompt builder (assertion) and the system prompt (generated from the same rows) — plus the golden test `tests/golden/review-prompts.test.ts`, which lints every rendered prompt across the three fixtures and every stage and `copy.review`. Document text is never linted or rewritten; it is quoted as written, even when the document itself says "you will be entitled".
- Grounding rule in the UI: every document-derived statement is rendered through `SourceCard` (or a future primitive built on `resolveClaim`), which refuses to show a claim with zero resolvable citations and shows an explicit withheld state instead; unresolvable extra citations are reported in the panel, not dropped. Callers pass a reader-facing `topic` label; `category` stays a machine key.
- Frontend rules: every sentence the product says lives in `features/journey/copy.en.ts` and `copy.hinglish.ts` (one `Copy` type; `copy.test.ts` pins that the tables have the same leaves, no empty line, and differ everywhere not on its English-on-purpose list); components import `copy` from `copy.ts`, a Proxy that resolves each section against the current language at read time, so never capture `copy.x` at module level (read it inside the component) and never pass a `copy` element created outside the route tree; `JourneyRoutes` subscribes to the display store, which is what re-renders every screen on a language change. The boundary text and the retention notice are safety copy, rendered verbatim and never promising behaviour the code lacks (the Hinglish table mirrors those commitments one to one); validation errors are inline, icon + text, `role="alert"`, linked with `aria-describedby`, and focus moves to the first bad control on submit (buttons are never disabled to block progress); visual system is "ink and paper" (paper background, ink-navy text, terracotta primary; Lora headings, DM Sans body — self-hosted fontsource files, not Google Fonts) defined as tokens in `src/index.css`, light and dark both kept AA-contrast.
- Accessibility bar (PRD §10, checked with axe + keyboard): each choice is a native `<button>` and its own Tab stop (no radio groups / roving tabindex), accessible name via `aria-labelledby` = label only with the long text in `aria-describedby`, landmarks header/main/footer, one h1, skip link first, no `maximum-scale` in the viewport meta, no emojis, no color-only meaning. On every route change `RouteFocus` (`features/journey/route-focus.tsx`, rendered after the route table inside `JourneyRoutes`) focuses the new screen's h1 (`tabindex=-1`, ring from `index.css`) unless the screen placed focus itself (safety heading, deletion notice); the packet has a visible-on-focus "Skip past the packet" link before its ~130 reference links, whose names read "Reference [n]", and each cited excerpt is a `tabindex=-1` landing point. `pnpm a11y` (`scripts/a11y/`, see `tests/README.md`) drives the three keyboard-only journeys in the system Chromium and runs axe in both schemes; run it after any change to a screen's controls.
- Display controls (FR-11, Task 7.2): `features/display/` — `display-store.ts` is a small external store (`{ locale: "en" | "hinglish", textSize: 100 | 115 | 130 | 150, theme: "light" | "dark" | "system" }`, persisted in localStorage under `clausecompass.display`, the reader's setting not the session's) that applies itself to the page: `<html lang>` = `en` / `hi-Latn`, root `font-size` = the percentage (the whole layout is rem-based, print resets it to 100%), the `dark` class + `color-scheme` on the root for the theme ("system" follows `prefers-color-scheme` as it changes; the dark tokens in `index.css` are screen-only so the packet prints on paper; `index.html` applies the stored theme before the first paint). `SettingsMenu` (in `SiteHeader`'s right-hand control group on every screen, before the account control; hidden in print with the header) is a gear button (`aria-expanded`/`aria-controls`) opening a named `<section>` panel (kept in the tree, `hidden` while closed; Escape returns focus to the gear, an outside press or focus leaving it closes it) with the language buttons (`aria-pressed`, each with its own `lang`), the text-size steppers (`aria-disabled` at the ends, `aria-live` readout), the theme buttons, and links to `/help`, to `VITE_FEEDBACK_URL` (row omitted unless set to an `https:`/`mailto:` address) and to the boundary statement on the welcome screen (`/#boundary-heading`; omitted on the safety screen, whose header has no way home). While Hinglish is on, the header shows the convenience note in a strip under its row, on the screen itself rather than inside the panel. The Responsible Language lint runs over the English table only; the Hinglish table is reviewed by hand. Read-aloud (`features/speech/`): browser `SpeechSynthesis` only, nothing leaves the tab; `ReadAloudButton` renders nothing where the API is missing, one reading at a time (starting one cancels another, leaving the screen stops it), utterances chunked to ≤ 200 chars in `en-IN`, and a failure before anything was heard shows a `role="status"` line under the button instead of silence. ## Gotchas

- Run `pnpm check:size` before commits that add fixtures or docs. Hard limit is 3 MiB internally (hackathon cap 10 MB; raised from 2 MiB on 15 Sep 2026 when source and tests alone passed it). `pnpm-lock.yaml` alone is ~200 KB.
- The repo will be public: never commit real documents. `samples/real/` and `attached_assets/` are git-ignored; copy what is needed into `docs/` or `samples/` deliberately.
- `docs/PRD.md` contains internal hackathon-strategy notes (§0, §7.3(a), §13). Trim them before the repo goes public, or keep a cleaned copy.
- Both dev servers refuse to start if `PORT` (and `BASE_PATH` for the web) is missing; on Replit the workflows set them, locally `pnpm dev` does. Do not hard-code ports.
- The Vite `/api` proxy is only active when `API_PROXY_TARGET` is set (only the local runner sets it). On Replit the platform proxy routes `/api`; do not add another proxy.
- Sessions (FR-12, Task 5.1). One session = one reader's visit, opened at the upload screen's Continue by `POST /api/sessions` (multipart `stage`, optional `documentType`, `file` or `older`+`newer`; 201 with `{ id, stage, documentType?, ttlMinutes, expiresAt, documents[{ slot, name, summary }], outputs{ documentMap, reviewPrompts, compare } }`). The store (`src/sessions/store.ts`) is in memory: extracted text and chunks only, never the raw bytes; sliding TTL of `SESSION_TTL_MINUTES` touched by every request that names the session (`GET /api/sessions/:id` exists for that), an unref'd sweep plus a check on read, `MAX_SESSIONS` (100) → 503 `busy` with `Retry-After`. `DELETE /api/sessions/:id` is 204 whether or not the id existed and aborts preparation in flight (its completion then finds no session and answers 404). Outputs are computed once per session with in-flight de-duplication; a degraded `model-unavailable` output is returned but not cached, so a retry can do better. After expiry or delete every session route answers 404 `session-not-found` with the reader-facing "This session has ended" message. Session ids are masked in request logs (`lib/log-url.ts`). Consequence: the API must run as a single instance (no autoscale fan-out) until the store moves to a shared backend. `GET /api/sessions/policy` publishes `ttlMinutes` for the client's copy. Client side (`features/journey/journey-context.tsx`): a session belongs to exactly the files it was opened with — replacing or removing a file, changing stage or resetting ends it on the server (best-effort DELETE, query cache dropped); a page refresh cannot resume it (files live in memory), so the stored orphan id is deleted at boot; the footer's "Delete my document now" is the FR-12 control (awaits the 204, clears the journey and the query cache, lands on `/` with a one-time notice; on failure the control stays and says the TTL still applies); the provider mirrors the server clock — a route change touches the session (≥ 5 s apart) and a timer at `receivedAt + ttlMinutes` (or the tab becoming visible after that) ends it locally with a DELETE and sends the reader to `/upload` with a "Your session ended" notice, files still selected, so the browser's copy never outlives the server's and an open tab never keeps a session alive; an out-of-band 404 on an analysis screen shows the ended message with "Upload the document again" instead of a retry. The upload screen guards its own race: a response whose files no longer match what is on screen (or that arrives after the screen was left) is deleted rather than installed.
- Safety escalation (PRD §8, Task 5.3). The decision flow runs in the browser (`features/journey/flow.ts` over `@workspace/rules`). The interview's free-text answer is scanned on Continue by `say()`; the words never leave the tab (no API route receives interview text), are not stored, and are not kept in memory either: `say()` drops the cues (and the substrings they matched) from the escalation as it happens, sessionStorage holds only `{ category, guidance, origin }`, and the screen never shows anything typed back. On the escalating transition the provider drops the files, ends the session on the server (DELETE, awaited into a `setAside` status the screen words truthfully: "being deleted" / "has been deleted" / "could not confirm … deleted on its own N minutes after your last action") and stores `{ stage, sessionId: null, safety }` under the journey key, so a refresh restores the escalated flow (with the deletion status unknown, so unstated). `RequireNotEscalated` is outermost on every route but `/safety` and `/help` — Welcome, the steps, the dev gallery and not-found included — and `RequireEscalation` sends `/safety` to `/` when nothing escalated. Escalation is absorbing: the one exit is "Start again from the beginning" (`reset()`, which clears the flow before Welcome renders); `setStage` also starts a fresh flow as defence, but Welcome is not reachable while escalated. The interview navigates to `/safety` with `replace`, so Back cannot return to the question. There is no server-side gate because the server never sees the trigger text; the session deletion is the guarantee that no analysis runs on that document. The safety screen shows numbers only through the registry (`resourceForGuidance`); its copy names no number, no partner and no advice. `tests/safety/escalation-fixtures.test.ts` pins fixture → decision → route, the word-dropping, the stored shape's round trip, the rendered body's links (registry contacts only, none to a journey step, nothing typed) and the copy lint; `tests/safety/escalation-routing.test.tsx` mounts the real routes and provider in happy-dom and proves the acceptance line end to end (fixture → `/safety` with the session's DELETE the only request, every other address bouncing, refresh, the unconfirmed-deletion wording, the calm fixture going on to the map).
- `lib/db` needs `DATABASE_URL` at import time; nothing imports it, so the API boots without a database. Sessions are in memory (see above). Decide before submission: move the session store to Postgres (needed for autoscale) or remove `lib/db` and `scripts/post-merge.sh`'s `db push` step.

- The root `vitest.config.ts` aliases `@/` and `@samples/` to the web app's paths so its pure helpers (`features/analysis/*.test.ts`, `features/packet/*.test.ts`, `features/journey/flow.ts`) run in the node environment, and sets `esbuild.jsx: "automatic"` so `tests/export/packet-export.test.ts` can render `PacketDocument` with `react-dom/server` (`react`, `react-dom` and `@workspace/api-zod` are root devDependencies for that test only). - Export artefact scan (FR-09 acceptance): `tests/export/packet-export.test.ts` boots the real app with the mock provider, builds the packet from the actual JSON of both endpoints for each fixture, renders HTML and text, and fails on anything that looks like the API payload rather than reader prose — identifier-shaped keys and values taken from the payload itself, JSON structure, `[object Object]`/`undefined`/`NaN`, raw ISO dates, confidence decimals, system-prompt lines, tool names, credential shapes — plus a prompt-injection fixture (script/handler/instruction text spliced into a clause must come out escaped, never executed) and the Responsible Language lint over `copy.packet` (the notice's own "whether a clause is legal or fair" sentence is the one deliberate exception, pinned to the boundary copy). - `pnpm test` starts the real Express app on an ephemeral port for the route tests; those tests set `PORT`/`LLM_PROVIDER=mock`/`AUTH_PROVIDER=mock`/`LOG_LEVEL=silent` before importing `app.ts` (`tests/support/api-server.ts`, `TEST_ENV`), and the root `vitest.config.ts` sets `VITE_AUTH_PROVIDER=mock` so every mounted screen uses the mock auth client. Raw-fetch tests send `readerHeaders()` (bearer `mock:<TEST_READER_UID>`); happy-dom suites wrap the tree in `AuthProvider` and call `signInTestReader()` (`tests/support/auth.ts`) per mount. `TEST_READER_UID` is `MOCK_GOOGLE_USER.uid` on purpose: a session a test helper opens must belong to the reader the mounted screens sign in as, or the screens see 404. Test-only helpers live in `artifacts/api-server/src/testing/` and are not imported by the bundle.
- A happy-dom suite cannot boot the API in-process: vitest rewrites `import.meta.url` inside the server's modules to `http://localhost:3000/...` under a DOM environment, so the extraction worker (`extraction/isolated.ts`, located from `import.meta.url`) fails with "The URL must be of scheme file" and every upload answers 500. Such suites use `bootApiProcess()` (the same app under tsx in a child process, `tests/support/api-process.mts`) and reach it over TCP; happy-dom's `fetch` handles absolute URLs but resolves relative ones against a port nothing listens on, and encodes `FormData` in a way the multipart parser rejects, so uploads go over node:http (`openSession`).
- Prompt-leak guard (Task 6.1): `validateModelOutput` takes `instructions` (the API passes `PROMPT_INSTRUCTIONS`: system policy, every fixed label of the user message, the tool's name and description and the schema's field descriptions (`MODEL_OUTPUT_DESCRIPTIONS`) — not the task line or the reader's question) and rejects as `instructions-echoed` a claim that recites them: a run of eight consecutive words inside the claim or across the reply's claims read in order; a claim of 3–7 words that is wholly instruction text (whole-word match); a window of 16 words (the whole claim when shorter, or the eight words either side of a claim boundary) of which ≥ 70% are found in order within a nearby span of the instructions (a recital with a word changed or filler added every so often); a sub-3-word instruction such as the tool name wherever it appears. Checked after the quote checks, before the language lint; the detail sentence never echoes the prompt. It exists because the injection fixture's "reveal the system prompt" clause produced a claim reciting the policy that passed every other check. A recital altered every third word or paraphrased is not caught (nothing in the prompt is secret); a real model writing eight policy words in a row is the false-positive risk; the goldens are unaffected.
- Upload hardening (Task 6.2): the extension is the file's claim and the magic bytes must agree (`sniff.ts`; the MIME header is only a fallback when there is no extension and is never trusted on its own), so a PDF named `.txt` or a PNG named `.pdf` is 415 `format-mismatch` whatever the header says. A zero-byte file is 422 `empty` before any type check. multer's defaults were changed on purpose in `uploads/multipart.ts`: `preservePath: true` because busboy would otherwise reduce `../../etc/passwd` to `passwd` before the API could see and refuse it, and `defParamCharset: "utf8"` because the default Latin-1 turns a Devanagari file name into mojibake. multer also decodes `%0A`/`%0D`/`%22` back into the name, so a newline can arrive that way and is refused as a control character; a NUL in the header never gets past busboy (400 `bad-upload`). The cleaned name (`safeFileName`: direction overrides such as U+202E stripped, whitespace collapsed, capped at 120 with the extension kept) is what extraction sees and what the session shows, so the two never differ. `tests/adversarial/upload-hardening.test.ts` sends the four PRD §9 cases to both routes; refusal messages never repeat the name back.
